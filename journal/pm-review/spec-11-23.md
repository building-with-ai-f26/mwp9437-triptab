# Build spec: Mike's 11/23 ski trip test

Written 11/24 by Claude as product manager, from Mike's own notes on setting up the real ski trip on triptab.org the evening of 11/23. This file is the checklist a build session works from and checks its work against. It is the durable list: the runbook's Steps row points here, and calls Mike hasn't answered stay in the runbook's Open calls, not here. C58 to C61 were decided 11/24 and are written into the items below.

## How a build session uses this file

1. Read this file, then the runbook's Decided calls (C58 to C61, 11/24). Build in wave order. Finish and verify one item before starting the next.
2. An item marked **Waits on Cnn** is not built until that call is in Decided calls. If Mike's answer differs from the recommendation written here, rewrite the item's Behavior and Checks here first, in the same pull request.
3. An item is done only when every check under it is ticked, each with its evidence: a test name, a click-through screenshot at 1280 and 390, or an eval result file in `journal/evals/`. Then fill its row in the Completion table at the bottom.
4. Nothing here rewrites or deletes production data. Where a fix needs that, it is listed under Needs Mike's OK and waits.
5. Before the last merge, have a fresh agent read only this file and the diff (not the build session's summary) and list any check that isn't met. Fix what it finds.
6. Fixtures, evals and screenshots use made-up trips, names, amounts and booking codes. Never commit the real booking emails, codes, amounts or friends' names.

### T2. Own-pay plans: your own price and your own status

**Decided by Mike, C61 and 11/24 in chat:**
- Don't make people add a price. Someone who joins a plan where everyone pays their own only needs the ability to add theirs, and must never get the price Mike paid.
- The status is per person: Mike, who booked, sees Confirmed; a friend who joined but hasn't booked sees Planned.

**What the code does today.**
- [Code] The card's price on an own-pay plan is only your own line (`app/src/pages/TripPage.tsx:440-443`), and each person can log their own cost in the plan's panel (`app/src/components/trip/PlanPanel.tsx:353`, `log_own_line`). So the price part already works.
- [DB] The friend who joined both flights on 11/23 has no price on either; the only expense on each is Mike's. Nothing was copied.
- [Code] The status is one for the whole group: an own-pay plan reads Planned, "1 of 2 booked", until everyone going has booked (`TripPage.tsx:452-461`, `ownProgress`). That is why Mike's overnight flight went from Confirmed to Planned for him when the friend joined. This is what changes.

**Behavior.**
- No prompt after Join; adding your price stays optional. Mark as booked works with the price left blank (it starts blank; the plan's estimate is only a hint), and a booking with no price shows no "$0".
- On a plan where everyone pays their own, the status you see is your own: Confirmed once you have booked (marked yourself booked or logged your cost), Planned until then. A Suggested plan stays Suggested for everyone.
- Everywhere the status shows follows the same rule for the person looking: the card's look (solid card and stripe, the green "$ ✓" when your own cost is paid), Your plans, the plan's panel, the week view and the calendar export.
- The booked count ("1 of 2 booked") still shows beside it, so everyone sees who hasn't booked yet.
- Dropping yourself from an own-pay plan takes your own line with it (only yours); an Owner taking someone else out leaves that person's line alone.
- A plan nobody has logged a line on keeps its stored status, so an Owner's hand Confirm (C21, C26, C27) stays as it was.
- Split-bill plans keep one status for the whole group, as now.
- Prefer working out each person's status in the app from what is stored (who booked, own cost lines) over storing a status per person. If a migration turns out to be needed, it is additive and runs on TripTab dev first.

**Checks.**
- [x] Unit test of the per-person status: booked gives Confirmed; joined but not booked gives Planned; a Suggested plan stays Suggested for both; a split-bill plan is unchanged. Evidence: `statusFor` in `app/src/lib/ledger.ts`, tests "each person's own status on own-pay plans (T2)" in `ledger.test.ts` (7 tests).
- [x] Click-through on TripTab dev with two accounts, at 1280 and 390: A logs a price on an own-pay flight and books it; B joins. A sees Confirmed with A's price; B sees Planned with no price (not A's); both see "1 of 2 booked". Evidence: `e2e/own-status-flow.cjs`, `docs/screenshots/own-status-*`.
- [x] B marks themselves booked, with or without a price: B now sees Confirmed, and A's view doesn't change. Evidence: the same flow (B books with no price).
- [x] B adds their own price from the plan's panel; A's price stays as it was. Evidence: the same flow.
- [x] Your plans and the week view show the same status as the card for each person. Evidence: the same flow reads all three for both people at each step.
- [x] B taps Drop: only B's line (if any) goes, and A still sees Confirmed. Evidence: the same flow. `who-pays-flow` now expects "Confirmed for you" for the booker.

### T13. Google star ratings on idea cards

**Waits on C65.** From Mike, 11/24: suggestion cards should show Google's review stars.

**Why it needs a call.** Stars can't come from the AI; it would be guessing, and the AI rules forbid inventing. They have to come from Google's Places API, which needs a Google Cloud billing account and an API key. Asking for a rating bills the call at an Enterprise tier. Read 11/24 on Google's pricing pages: Place Details Enterprise has 1,000 free calls a month, then $20 per 1,000, and the old $200 monthly credit ended in February 2025. Text Search is billed under its own SKU, which wasn't checked. Our use is a few hundred calls a month at most, so it should be free, but Mike's money rule needs his yes and a hard cap before the first call.

**Behavior (if C65 is yes).**
- For each idea, the Edge Function makes one Places API Text Search call for the place's name and address, asking only for `id`, `rating`, `userRatingCount` and `googleMapsUri`. It never asks for `reviews`, which is billed at a higher tier.
- The card shows the stars and count ("4.6 ★ (812) on Google"), with Google's attribution. Its Google Maps link becomes `googleMapsUri`, the exact place, instead of T12's search link.
- No match, an error or the cap reached: the card shows no stars, keeps T12's search link, and the idea is not dropped.
- Per Google's terms, only the place id is stored with a saved plan, never the rating. Stars show on idea cards (Plan with AI and Ask AI), not on saved plans.
- The key is a Supabase secret Mike enters himself. It is restricted to the Places API, and its name shows in `ai-status`.
- Hard cap: a daily quota on the Places API in Google Cloud of 33 requests a day (about 1,000 a month, inside the free tier), plus a $1 budget alert. Mike sets both from a laptop step list before the first call.
- Each lookup is logged with its cost so spend shows in the build log.
